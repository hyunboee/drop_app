## 1. 개요

### 1.1 전환 배경

웹 MVP를 실기기(Galaxy S25 Ultra, Android Chrome)에서 테스트해 드롭 흐름(가입 → 권한 → 사진 선택 → 위치·방향 지정 → 업로드 → 게시)이 동작함을 확인했다. 같은 테스트에서 웹(AR.js 위치 기반)으로는 풀 수 없는 문제 세 가지가 드러났다.

| # | 문제 | 실측·관찰 | 원인 |
|---|---|---|---|
| N-P1 | 캡슐이 매번 같은 자리에 보이지 않는다 | 프레임이 GPS·나침반 값에 따라 떠다닌다 | GPS 좌표 + 방위만으로 배치한다(`2-PRD.md` Q-02). 평면·특징점 기반 앵커가 없다 |
| N-P2 | 걸어도 가까워지지 않는다 | 실내에서 5~6m 걷는 동안 GPS는 수십 초에 걸쳐 최대 5.2m만 따라왔고, 정확도가 3.7~11.4m로 흔들렸다 | 화면 속 내 위치가 GPS에만 의존한다. 카메라 기반 움직임 추적이 없다 |
| N-P3 | 카메라 화질과 안정감이 낮다 | 기본 영상이 640×480이었고 1920×1080으로 올린 뒤에도 기본 카메라 앱보다 떨어진다 | 브라우저가 넘겨주는 영상을 WebGL 텍스처로 다시 그린다 |

### 1.2 목표

- **N1 목표:** "드롭한 사람이 놓은 바로 그 자리에, 누가 언제 와도 같은 위치·방향으로 캡슐이 보인다"를 실기기에서 검증한다.
- 웹 MVP의 기능 범위(가입, 드롭, 검열, 주변 조회, 열람, 삭제)를 그대로 옮기고, AR 부분만 평면 스캔 + 클라우드 앵커로 바꾼다. 결제·보상 등 새 기능은 넣지 않는다(3.2).
- 백엔드(Express, PostgreSQL, S3, Rekognition)는 유지하고 필요한 만큼만 고친다(6장).

### 1.3 성공 지표 (KPI)

| 구분 | 지표 | 목표 |
|---|---|---|
| 위치 고정 | 드롭한 캡슐을 같은 장소에 다시 가서 봤을 때, 드롭한 자리와의 위치 오차 | NP-01 이내인 경우가 10회 중 8회 이상 |
| 위치 고정 | 다른 기기·다른 계정으로 봤을 때도 같은 자리에 보임 | 2대 기기로 같은 캡슐 5개 확인, 모두 NP-01 이내 |
| 움직임 추적 | 캡슐을 향해 걸으면 화면에서 연속으로 가까워짐(툭툭 끊기지 않음) | 실내·실외 모두 성공 |
| 앵커 인식 | 현장 도착 후 앵커를 인식해 정확한 자리에 표시하기까지 걸리는 시간 | NP-03 이내인 경우가 10회 중 8회 이상 |
| 기능 동등 | 웹 MVP의 드롭 → 열람 전 흐름 | 네이티브 앱에서 성공 |

## 4. 기능 요구사항

우선순위: P0 = N1 필수, P1 = N1 여유 시

| ID | 요구사항 | 우선순위 | 수용 기준 |
|---|---|---|---|
| FR-N01 | 가입·로그인 | P0 | 규칙은 `2-PRD.md` FR-01과 같다(필수 동의 3개, M-04·M-05·M-10, 401·409·429). 다른 점: 세션 토큰을 쿠키가 아니라 `Authorization: Bearer <토큰>` 헤더로 보낸다. 앱은 모든 요청에 `X-Client: app` 헤더를 붙이고, 서버는 이 헤더가 있을 때만 로그인·가입 응답 본문에 토큰을 담는다(웹 응답에는 토큰을 싣지 않는다). 세션 확인 미들웨어는 쿠키와 헤더를 모두 받는다(웹 호환 유지). 앱은 Android Keystore에 만든 AES-GCM 키로 토큰을 암호화해 암호문만 앱 저장소에 둔다(평문 저장 금지, 지원이 끝나는 `EncryptedSharedPreferences`는 쓰지 않는다). 다시 켤 때 `GET /api/me`로 유효성을 확인한다 |
| FR-N02 | 권한 획득 | P0 | 카메라와 위치(정확한 위치) 권한을 요청한다. 둘 다 필수이며 하나라도 거부하면 권한 안내 화면과 재시도·설정 열기 버튼을 보여 준다. 방향 센서 권한 화면은 없앤다(Android는 별도 권한이 없다). ARCore를 지원하지 않는 기기나 "Google Play AR 서비스"가 없으면 안내 화면을 보여 준다. AR 화면에 처음 들어갈 때 구글이 요구하는 고지 문구 "To power this session, Google will process sensor data (e.g., camera and location)."와 "자세히 알아보기" 링크(10장 V-07)를 눈에 띄게 보여 준다(NFR-N06) |
| FR-N03 | 평면 스캔과 프레임 배치 | P0 | 드롭을 시작하면 사진 선택(FR-N04) 뒤 AR 화면에서 평면(바닥·벽·탁자)을 찾는다. 평면을 1개 이상 찾기 전에는 "주변을 천천히 비춰 주세요"를 안내하고 배치를 막는다(BR-04, 5.4 planeScanMatch). 평면을 탭하면 고른 사진을 담은 미리보기 프레임이 그 자리에 놓이고, 끌어서 옮기고 회전 슬라이더(0~359°)로 방향을 정한다. 벽면에 놓을 때는 슬라이더를 숨기고 벽이 바라보는 방위를 `heading`으로 쓴다(실증에서 벽 배치가 안 되면 N1에서 뺀다, RISK-N03). 프레임은 사용자 위치에서 드롭 배치 반경(PRM-20) 밖으로 나가지 않는다. GPS 정확도가 재측정 기준(PRM-03)보다 나쁘면 드롭을 막는다(서버 422 `LOW_ACCURACY`, `DROP_TOO_FAR`는 `2-PRD.md` FR-03과 같다) |
| FR-N04 | 사진 선택·업로드 | P0 | 갤러리에서만 사진 1장을 고른다(BR-05, 촬영 옵션 없음). Android 시스템 사진 선택기를 쓰므로 저장소 권한을 요청하지 않는다(NQ-08). 앱이 JPEG 재인코딩(M-13)과 썸네일(M-07) 생성을 하고 EXIF 위치정보를 지운다. 업로드 방식·검증·재시도·S3 키·태그는 `2-PRD.md` FR-04와 같다 |
| FR-N05 | 클라우드 앵커 저장 | P0 | "여기에 놓기"로 확정하면 앱이 그 자리의 주변 특징점을 스캔해 클라우드 앵커로 저장(호스팅)한다. 스캔 품질(`estimateFeatureMapQualityForHosting`)이 NP-04에 이를 때까지 "프레임 주변을 돌며 여러 각도에서 비춰 주세요"와 진행 정도를 보여 준다(제자리에서 폰만 돌리는 것은 효과가 없다). 저장이 끝나면 클라우드 앵커 ID를 받는다. 저장에 실패하거나 NP-05를 넘기면 다시 스캔하게 한다. 앵커 보관 기간은 캡슐 유지 기간(PRM-06 브론즈) 이상으로 요청한다. 그 자리에서 `checkVpsAvailabilityAsync`가 `Available`이면 그 순간의 Geospatial 포즈(위도·경도·고도·회전)도 함께 구한다(아니면 생략, RISK-N02) |
| FR-N06 | 게시 | P0 | 앱이 앵커(프레임 GPS 좌표, 방향 `heading`, 사용자 GPS 좌표·accuracy), 제목(M-11), 미디어 ID, 클라우드 앵커 ID, (있으면) Geospatial 포즈를 한 번에 게시 요청한다. 검열·멱등·응답은 `2-PRD.md` FR-06·FR-07과 같다. 서버는 클라우드 앵커 ID와 Geospatial 포즈를 검증 없이 저장만 한다(형식·길이만 확인). 서버는 두 값을 선택 입력으로 받는다(웹 호환, NQ-09). 클라우드 앵커 저장에 성공하기 전에는 **앱이** 게시 요청을 보내지 않는다(NQ-04) |
| FR-N07 | 주변 조회와 표시 | P0 | 주변 조회 API는 `2-PRD.md` FR-08 응답에 클라우드 앵커 ID와 Geospatial 포즈를 더해 돌려준다. 앱은 캡슐까지 거리가 앵커 인식 시작 반경(NP-02) 안이면 가까운 순서로 NP-07개까지 클라우드 앵커 인식을 시작하고, 반경을 벗어난 앵커는 인식을 취소해 자리를 비운다. 표시 위치는 다음 순서로 정한다. ① 클라우드 앵커 인식 성공 → 그 자리·방향에 고정 ② 실패했고 Geospatial 포즈가 있으며 현재 VPS를 쓸 수 있음 → 그 포즈에 고정 ③ 둘 다 안 됨 → GPS 좌표 + `heading`으로 그리고 "대략적인 위치예요"를 표시한다. ①·②로 고정된 뒤에는 GPS 값이 흔들려도 프레임이 움직이지 않는다. 걸을 때의 화면 속 이동은 ARCore의 움직임 추적을 따른다(N-P2 해소) |
| FR-N08 | 캡슐 열람 | P0 | 서버 판정은 `2-PRD.md` FR-10과 같다(판정식, 401 → 400 → 404 → 422 → 403, 열람 기록, 미디어 프록시). 요청에 `plane_match`(클라우드 앵커 또는 Geospatial로 고정된 상태에서 탭했는지)를 더해 열람 기록에 저장한다. N1에서는 `plane_match`가 false여도 GPS 판정만 통과하면 열람을 허용한다(NQ-06). 원본 이미지는 앱이 기기 캐시에 저장해 같은 캡슐을 다시 열 때 내려받지 않는다(`2-PRD.md` NFR-05의 네이티브 대응) |
| FR-N09 | 미니맵 | P0 | AR 화면 우측 상단에 내 위치(가운데), 보는 방향(위쪽), 주변 캡슐 점, 열람 반경(PRM-01) 원을 그린다. 가장자리는 NP-06이며 더 먼 캡슐은 가장자리에 붙인다. 열람 가능한 캡슐은 밝게 표시한다(웹 `MiniMap`과 같은 규칙) |
| FR-N10 | 내 캡슐 삭제 | P1 | `2-PRD.md` FR-11과 같다. 삭제 시 클라우드 앵커도 지울지는 NQ-07 |
| FR-N11 | 로그아웃 | P0 | 홈(NW-16) 아래의 "로그아웃"이나 FAB 메뉴에서 로그아웃하면 서버 세션을 지우고 기기에 저장한 토큰을 지운다 |
| FR-N12 | 홈(관리 화면) | P0 | 로그인하면 카메라보다 먼저 홈을 보여 준다. 왼쪽 위에 등급별 캡슐 수("브론즈 5", "실버 0"), 오른쪽 위에 접속한 사용자 이름(이메일의 @ 앞부분)과 첫 글자 표시. 그 아래에 숫자 세 개(남긴 캡슐, 열어 본 캡슐, 곧 만료 NP-08), "내가 남긴 캡슐" 목록(썸네일, 제목, 열람 횟수, 등급과 남은 날 "브론즈 D-3", NP-09개 미리 보기 + 전체 보기), "보관함" 미리 보기(NP-09), 맨 아래 고정 버튼 "AR 카메라 열기". 목록은 Active 캡슐만이다. 등급별 캡슐 수의 뜻은 NQ-11 |

| FR-N15 | AR 길찾기 | P1 | 지도에서 캡슐 표식을 고르고 "AR 길찾기"를 누르면 AR 카메라가 켜지고, 화면 가운데에 그 캡슐 쪽을 가리키는 화살표와 남은 거리("'제목'까지 120m")가 뜬다. 화살표는 내 위치(GPS)와 폰이 보는 방향(나침반)으로 돌아간다. NP-11 안으로 들어오면 화살표 대신 "도착했어요 · 주변을 비춰 찾아보세요"를 보여 준다. "길찾기 끝내기"로 끈다. 길(도로)을 따라가는 안내가 아니라 직선 방향이다 |

| `GET /api/capsules/archive` | `{ capsules: [{ id, title, thumb_url, media_url, opened_at }] }`. 세션 유저가 연 Active 캡슐, 최근에 연 순서. 같은 캡슐은 한 번만 |

## 7. UX 원칙

`2-PRD.md` 7장(풀스크린 AR, FAB 하나, 바텀시트 흐름, 정확도 배너, 상태 한 줄)을 유지한다. 달라지는 점만 적는다.

- **드롭 흐름:** FAB → 사진 선택 → 평면 찾기 → 프레임 놓기·방향 정하기 → 주변 스캔(앵커 저장) → 제목 입력 → 업로드·검열 → 완료. 주변 스캔 단계가 새로 생긴다.
- **스캔 안내는 구체적으로 한다.** "주변을 천천히 비춰 주세요"(평면 찾기), "프레임 주변을 여러 각도에서 비춰 주세요"(앵커 저장)처럼 무엇을 해야 하는지 말하고 진행 정도를 보여 준다.
- **고정 상태를 구분해 보여 준다.** 클라우드 앵커·Geospatial로 고정된 프레임과 GPS로만 그린 프레임(FR-N07 ③)을 시각적으로 구분하고, 후자에는 "대략적인 위치예요"를 붙인다.
- **앵커 인식 중에는 기다리게 하지 않는다.** 인식이 끝나기 전에도 GPS 기준 위치에 프레임을 먼저 그리고, 인식되면 제자리로 옮긴다.
- 방향 센서 권한 화면(웹 W-03의 일부)은 없앤다.
